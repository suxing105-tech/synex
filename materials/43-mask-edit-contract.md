# 43 · 再次创作的遮罩编辑（2026-11-12）

单图局部重绘那条工作流随包内置，代价是它依赖一套第三方（孤海工具节点）的私有约定；把「画遮罩」
做进再次创作弹窗之前先把这套约定钉死成文档，后面排查静默失效只照这一份对。

## 1. 遮罩到底怎么进工作流（孤海契约）

出处：`custom_nodes/Goohaitools-comfyui/nodes/加载图像.py`。

| 事实 | 位置 | 后果 |
|---|---|---|
| `LoadImageGoohai.RETURN_TYPES = ("IMAGE","MASK","STRING")`，MASK 是第 2 个输出 | `:40` | 槽位检测按「有没有 MASK 输出」认遮罩位，不看节点名 |
| `is_clipspace = "[input]" in str(image)` | `:158` | 上传时路径值必须以 `  [input]` 结尾，否则不走剪贴板分支 |
| 文件名不含 `clipspace-mask-` 时，透明区会被刷白 | `:217-220` | 遮罩文件必须叫 `clipspace-mask-<digest>-<n>.png`，命名是功能的一部分 |
| `MASK = 1 - alpha/255` | `:256-295` | 我们交出去的是「透明 = 要改」的透明 PNG，不是黑白图；黑白只在预览/导出时现推 |
| `IS_CHANGED` = 文件 sha256 | `:314-329` | 换一次遮罩就是换一份文件，天然不命中旧缓存；同名不同内容也认得出来 |
| 涂到的像素 < 10 时按全白处理 | 同上 | 前端 `MASK_EMPTY_PIXELS = 10`：低于它算「没画」，别交一份等于没画的遮罩 |

官方 `LoadImage` 同样是 alpha→MASK（根 `nodes.py:1747/1772`），但 `LoadImageMask` v1 不吃 alpha
（`nodes.py:1795/1824`），所以**别人导入的 `LoadImageMask` 类工作流仍然不支持**，检测也不会把它
标成遮罩位。这条是能力边界，不是 bug。

## 2. 槽位的四条新约定（前后端同名）

| 键 | 含义 | 谁写 | 谁读 |
|---|---|---|---|
| `mask: "alpha"` | 这一格的图能吃遮罩 | 检测 `clone_templates._mask_consumers`（顺着 MASK 输出找消费者） | 前端决定画笔出不出、后端决定收不收这格的 masks |
| `allow_empty: true` | 提示词留空是一个模式（这条工作流＝移除） | 随包模板写死 | `canGenerate` 放行 + 后端把「留空」从 422 改成按槽位判 |
| `empty_hint` | 留空时到底干什么，一句话 | 用户自己导入的模板可写 | 卡底常驻那行、编辑层顶栏的提示。**随包那条不写**：两个模式共用一句固定文案，多一块解释是噪音（见 §9） |
| `sync_to: [[node,input],…]` | 一颗旋钮管多台节点（两台采样器的步数） | 检测 | 前端写值时一起写、后端回填 |

**扩位继承母槽**：一台加载器克隆出来的第 N 个参考位照样带 `mask`，`referenceCells()`
（前端）与 `reference_cells()`（后端）同口径。丢了这条，扩位那一格就悄悄不能画遮罩。

## 3. 一次带遮罩的生成走什么路

1. 前端 `MaskEditor` 画完 → `MaskEdit{png(裸 base64 透明 PNG), tint, coverage, pixels, imageId}`。
2. `maskRequestPayload()` 只带真画过的格子；一张没画就整个 `masks` 键都不出现（老请求体一字不改）。
3. 后端 `decode_mask_png`：剥 `data:` → 空报「是空的」→ >12MB 拒 → 解不开报「不是读得开的图片」→ 长边 >4096 拒。
4. `compose_mask_png`：把遮罩按参考图尺寸 LANCZOS 对齐，`RGB + putalpha(invert(L))` 合成透明 PNG。
5. 上传文件名保留 `clone_sources` 那份源图 sha1[:8]，前缀 `clipspace-mask-`，值尾加 `  [input]`。
6. `masks` 不进 `public_state()` 白名单 → 不广播、不落库：它是这一次的参数，不是任务的一部分。
7. `ValueError → 400`、`CloneUnavailable → 409`、`KeyError → 404`（`routes/clone.py:332-336`）。

## 4. 编辑器的四条设计（定了就不动摇）

1. **画布只看 alpha，给人看的那层是它现染出来的副本**：涂没涂到是唯一事实，`.me-ink` 不是一份
   独立的事实，每次重画都从遮罩层整层拷过去、按叠色压一次浓度、再 `source-in` 换成 `MASK_INK_RGB`
   （`paintInk()`）。提交那份黑白图在导出时用 `fill 黑 → destination-out 画 mask → destination-over 填白`
   三步现推（逐像素循环在 4096² 上会卡手）。所以「换个颜色」「调叠色不透明度」永远不会悄悄改变
   送给 ComfyUI 的东西；反过来，这一层的**颜色必须与工作流盖给模型看的那份一致**（见 §9、§11）。
2. **撤销不存像素快照**：2048² 的 RGBA 一张 16MB，存 40 步就是 600MB。这里存笔迹
   `Stroke{op,r,pts}`，撤销/重做/清空/改叠色都走整条重放。
3. **手势与图库放大层对齐**：左键画、**Shift+左键框选加一块**、**Alt+左键框选减一块**、滚轮缩放、
   Ctrl+滚轮改笔刷、双击 100%⇄适应、空格临时抓手、`B`/`E`、`Ctrl+Z`/`Ctrl+Shift+Z`/`Ctrl+Y`、`+−0`。
   左键归画笔，所以平移只能靠空格或中键；Shift 与 Alt 那两下专门给「圈一整块 / 挖掉一块」，
   与孤海那台遮罩编辑器的两个修饰键同口径。谁算框选、算加还是算减，是 `lib/mask.ts` 的
   `maskRectOp()` 一把判的（Alt 抢在橡皮之前：手里是画笔也能直接挖，不必先按 `E`）。
4. **框选松手前一个字都不进遮罩**：拖动中只画在第三张画布 `.me-live` 上，松手才一次落进遮罩层，
   显示层随后由它派生（`Stroke{op,r,pts,rect}`，撤销重放走 `apply` 的 rect 分支；`op` 记的是这一框
   是加还是减，所以 Alt 减的那一块撤销一次就还原）。所以从右下角往回拖、拖过头
   直接松开都不会留下已涂的痕迹——这一点画笔做不到，画笔是一路 apply 下去的。
   框按画布坐标归一成正放矩形并裁进画面（`maskRectSelect`），两边都小于 `MASK_RECT_MIN = 2`
   当手抖，不进笔迹栈、不占一步撤销。

配套口径：画布尺寸 = 参考图尺寸，长边超 4096 先降；两个事件位置之间补点（否则快拖成虚线）；
`onDone(null)` = 这格其实全擦了，调用方连键一起删；换参考图/换工作流时那条遮罩作废并 toast 说明。

## 5. 交互上定了的几个歧义点

- **入口在哪**：大图左上角「画遮罩 / 改遮罩」。文案区分第一次和第二次，别让人以为进去是看一遍。
- **大图摆谁的图**：能画遮罩的那一格里的图，不是被点的那张卡。画遮罩必须看得见落点。
- **点进去之后**：盖住整块弹窗的一层（`.cm-backdrop` 的孩子、`.cm-panel` 的兄弟），不是挤在左栏里的一块。
- **改提示词怎么办**：编辑层里只读回显模式和提示词摘要，要改就退出编辑层——就地改会画完还得退出去。
- **跑完之后这一格给谁**：默认给新产出，右上角「回看参考图」切回去看范围落在原图哪儿，再点回来。
- **没画遮罩就生成**：放行，但先 toast 一句「这一次没有局部范围」；提示词全擦/遮罩全擦同理。
- **Esc**：第一下只退编辑层，按「取消」算，这次画的不要。
- **随包模板**：不给点「重新检测槽位」（后端 409），按钮留着说清原因。

## 6. 已知偏离与风险

- 原计划里的「手动勾选支持遮罩」没做：检测已经自动，手动强开一条 MASK 没人用的格子只会做出一份
  ComfyUI 会拒的图。要支持别的节点，正确做法是扩 `_mask_consumers` 的检测，不是给用户一个开关。
- 异机缺孤海节点、或缺 `万物移除Remove` / `一致性无偏移` LoRA 时，`/prompt` 会拒；这是模板依赖，
  不是遮罩链路的问题。
- alpha→MASK 是第三方私有约定，孤海升级可能静默失效。回归点：`<10 像素算空`、`clipspace-mask-` 前缀、
  `  [input]` 尾巴，三处任一变了都会「看着成功、其实整张重画」。
- 带遮罩的每次生成多一次上传 + 一次像素比对。
- 云端模板不吃本地透明 PNG，`maskTemplate` 直接排除。

## 8. 真跑才量出来的坑：底图是 feed 的 ?max=1024 预览

编辑器顶栏说「已涂 62290 处像素」，而实际送进 ComfyUI 的那张遮罩涂了 252182 个像素（约 4 倍）。
问题不在遮罩链路，在底图地址：列表接口的 `original_url` 本身就是 `?max=1024`
（`repository.original_url_for` 的 `max_size` 默认 1024，为的是 feed 少下一倍流量），
于是 1136×2016 的图进画布只剩 577×1024，画布跟着小图走：

- 滑杆写「直径 60，按原图像素算」，在 577 宽的画布上落半径 30，导出后又被 `compose_mask_png`
  拉回 1136 宽贴上去 → 实测一条 124 像素宽，是标称值的两倍，涂的位置和改的范围对不上；
- 「已涂 N 处像素」按画布数，面积少报 k² 倍；
- 遮罩边缘被重采样拉大一遍，精度一起丢。

改法两条，都进 `lib/mask.ts`：`maskBaseImageUrl` 把底图地址的 `max` 档位抬到画布上限
（长边 ≤4096 直接要原图，`fit` 去掉、cache-bust 的 `v` 留着）；`maskCanvasScale` /
`maskBrushRadius` / `maskPixelsInSource` 在真降过档（源图长边超 4096）时把笔刷半径与像素计数
换算回源图口径。口径定死一句：**`?max=1024` 那类降档地址只许用来显示，任何「按像素说话」的
编辑功能都得按参考图真实分辨率要底图。**

顺手修的一处：笔刷圈直径以前是 `brush * fit * zoom * 2`，而落笔半径是 `brush / 2`（直径就是
`brush`），圈比真正涂到的宽一倍，用户只能凭感觉把笔刷调小。

## 9. 「移除指令」为什么从界面上撤掉，以及那句里的颜色不能改（2026-11-12）

随包那条从这一版起改口叫**闪寻局部编辑**（旧名留在 `legacy_labels` 里，老库那条下次启动顺势改名，
记录不换）。「移除指令」那格输入框一并从槽位里撤掉，理由两条：

1. 它不是给用户改的。完整提示词留空本来就是走移除分支（`307 → 260 GoohaiAnyExists → 262 ifElse`
   选 212/252），弹窗里再摆一句「移除图像中的绿色区域」纯属重复解释；
2. 摆出来反而危险：改错一个字（哪怕只改颜色那两个字）移除就失灵，而没人会去查那格。

**那句指令里的颜色不能单独改。** 移除分支没有 MASK 直接进模型：`204 孤海-图像合并（遮罩）`把
`205 LayerUtility: ColorImage` 那张纯色图按 `透明度 0.4` 盖在遮罩区域上，再让 `118` 用
「移除图像中的X色区域」去指挥模型，而且这条分支上还挂着 `Qwen2.1_万物移除Remove_GH` 那颗 LoRA——
它是照这个配色训的。所以 205 的颜色与 118 的那句话必须同色，要换就一起换；
`test_the_removal_line_names_the_color_it_actually_paints` 把这条钉住了。

那编辑器这层显示色怎么办？**当天先按「只是给人看的」留着红，第二天就被推翻了**（见 §11）：
「给人看」不等于「可以随便给个颜色」——用户在屏幕上涂的是红、模型收到的是绿，他照屏幕上那层
理解那句指令必然对不上，这个不一致解释不掉，只能消掉。所以这一版把 `MASK_INK_RGB` 改成与 205
同一个绿（`0, 255, 0`），默认叠色也从 0.45 挪到 0.4，对齐 204 那颗 `透明度 0.4`：
不拖滑杆时，屏幕上这一层就是模型看到的那一层。改的是显示端，118 那句话与 205 那颗染色节点
一个字没动。

## 10. 只改槽位的更新，光比 `bundled_sha` 刷不进去

`bundled_sha` 只按 workflow 算。这一版撤掉「移除指令」槽位时正文一字没动，于是 sha 没变，
`seed()` 走到 `stored_sha == sha → skip`，用户库里那条会永远留着被撤掉的那格。
现在改成：正文没被用户改过时（`workflow_sha(存的) == bundled_sha`）**再比一次槽位**，
不一样就刷。内置那几条不给重新检测槽位（后端 409），所以「存的槽位与包里的不一样」
只可能是包更新过，不存在覆盖用户手改的问题。用例：`test_a_slot_only_update_still_reaches_an_untouched_builtin`。

## 11. 画笔、选框、遮罩区三种浓淡不一样：根因是显示层在累加 alpha（2026-11-12 第二轮）

苏醒的报法是「画笔颜色、画框颜色、遮罩区域得到的颜色不一致」。三个颜色其实一直是同一个
`MASK_INK_RGB`，不一致的是**浓度**，而浓度不一致是因为显示层是**一路累加**出来的：

- 画笔：`dab()` 沿着补间点连刷几十上百个圆，每个圆都 `globalAlpha = ink` 往 `.me-ink` 上叠。
  同一笔里圆点本来就互相重叠，`0.45` 叠三五层就接近实心（截图上那一笔是饱和的粉红）；
- 框选：`block()` 一下成形，只叠一层，所以是半透明红；
- 而重叠两块选框，重叠处又比单块更深（0.45 → 0.70）。

同一件事（「这里要改」）在屏幕上出现三种浓度，人就没办法靠眼睛判断自己圈到了什么。
**修法是取消「第二份事实」**：`dab`/`block` 只往遮罩层画（那边永远 `alpha = 1`，只有涂没涂到），
显示层每次由 `paintInk()` 从遮罩层整层派生——`drawImage` 时 `globalAlpha = ink` 一次定浓度，
紧接着 `source-in` 填 `MASK_INK_RGB` 换颜色（`source-in` 的结果 alpha = 源 alpha × 目标 alpha，
所以浓度不会被第二次乘上去）。这样浓淡只由「涂没涂到」决定，叠多少笔、叠几块都一样，
橡皮挖掉的地方也自动跟着没。

本机真量过一次（`outputs/mask-ink-derive/_probe.html`，Chrome `--headless=new --dump-dom`，
同一份「8 个重叠圆 + 两块重叠矩形」分别走两条路，数画布里出现的 alpha）：

| 写法 | 画内 alpha 的取值 | 最暗处 |
|---|---|---|
| 旧：每笔 `globalAlpha = 0.4` 往显示层累加 | 52 档，一路涨到 **234** | 92% 不透明，早就不透明了 |
| 新：从遮罩层派生 | 主体只有 **102** 一档（= 0.4 × 255），其余全是边缘抗锯齿像素（1~98） | 正好 40%，与 `ink` 说的一样 |

也就是说旧画法里「叠了几笔」会一路涨到几乎不透明，而框选那一下停在 102——同一个遮罩两种浓度，
肉眼看到的深浅根本不代表涂了多久，这条表就是那个 bug 的量化现场。

两个连带的口径：

1. **默认叠色 0.45 → 0.4**，对齐 204 的 `透明度 0.4`，让「不拖滑杆」这一档就是所见即所得；
   滑杆仍然只是让人看得清，不改送出去的东西。
2. **拖动中的预览用同一颜色、同一浓度**（`drawPreview` 的填充 alpha 从 `ink + 0.2` 改成 `ink`）：
   预览什么样子，松手就是什么样子，别让人按预览去猜结果。

`requestAnimationFrame` 合并重染：显示层是全屏合成，画笔一次拖每秒几十个事件，逐事件重染在
4096 那一档会卡手，所以热路径走 `syncInk()`（下一帧只做一次），`redraw()` 与 `finish()` 里
同步补一次，交图那一刻的 `tint` 不会停在上一帧。

颜色为什么选纯绿 `0, 255, 0` 而不是图2 那种柔一点的绿：这一层要的是「和模型收到的那份同色」，
`205` 写死 `#00ff00`，显示端跟着它才谈得上一致；好看是次要的，而且浓度本来就给了滑杆调。
**不做图2 那排绿/灰/黑色板**：多色只能改显示，改不了 205 盖给模型的那一层，做多色等于把
这一轮刚消掉的不一致重新造回来。
