# 苏醒图库自动更新实施方案

日期：2026-09-09。状态：规划，尚未接入更新服务，本文中的新增文件和版本均为拟议内容。

## 1. 推荐方案

采用 Tauri 2 Updater + 签名的 Windows NSIS 完整安装包 + HTTPS 版本清单。首期仅支持 Windows x64 正式安装版，稳定频道。

默认自动检查，发现新版后轻提示；用户选择下载，下载期间继续使用，下载完成后点击“退出并更新”。扫描、导入或数据库写入未完成时推迟安装。离线不影响本地图库，不要求 ComfyUI 开启。

Tauri 提供签名验证和更新接口，Windows 可复用 NSIS 安装包生成更新产物。具体接入以锁定的插件版本为准。[Tauri Updater](https://v2.tauri.app/plugin/updater/)

第一版不包含强制更新、后台无提示安装、增量补丁、多频道、跨平台和无条件自动回滚。后续依据实际分发规模追加。

## 3. 用户体验

设置增加“关于与更新”：当前版本、上次检查时间、检查更新按钮、自动检查开关。自动检查默认开启，主界面就绪后延迟约 15 秒，每 24 小时至多自动检查一次；手动检查可随时执行。失败采用退避重试，不弹连续错误窗口。

| 状态 | 用户看到的内容与操作 |
|---|---|
| 最新版 | “当前已是最新版本” |
| 发现新版 | 新旧版本、更新说明、“下载更新”“稍后提醒” |
| 下载中 | 下载进度、已下载大小；总大小未知时不显示虚假百分比 |
| 下载完成 | “更新已准备好，退出并更新”；可继续使用 |
| 正在导入 | “图片导入完成后可安装更新” |
| 检查失败 | “暂时无法检查更新，图库仍可正常使用”与重试 |
| 安装准备失败 | 清晰说明文件占用或备份失败；恢复正常使用 |
| 更新成功 | 首次打开轻提示版本变化，无重复引导导入 |

进度由 Rust 事件推送给前端。检查、下载、安装由同一个状态机管理，避免重复点击启动多个安装器。更新说明按文本显示，不执行远端 HTML。

```mermaid
flowchart LR
  A[正常使用] --> B[检查新版]
  B --> C[提示下载]
  C --> D[下载并验证]
  D --> E[用户选择退出并更新]
  E --> F[等待任务完成与备份]
  F --> G[停止后端并确认退出]
  G --> H[安装完整包]
  H --> I[启动新版并验证健康]
```

## 4. 先解决进程冲突，再开放自动安装

1. 单实例插件在其他插件之前注册，重复启动优先唤起现有窗口，避免再次启动后端。相同产品标识在不同路径、管理员权限和普通权限下必须实测。[Tauri Single Instance](https://v2.tauri.app/plugin/single-instance/)
2. 单实例机制无法约束没有该机制的历史安装。首次迁移识别已注册安装路径、当前执行路径和后端归属，提示用户选择保留的安装位置。安装到 D 盘也应原位更新，不再额外创建 C 盘副本。
3. 新版增加受控 shutdown 流程：停止接收新写入、等待活动任务、停止监听、关闭数据库，然后等待后端及 PyInstaller 启动器退出。
4. Windows 进程树管理可采用 Job Object，并保留已有父进程监控作为补充；必须实测正常退出、强制关闭及更新路径。不能仅认为 start_kill 调用成功等于端口已释放。
5. 进入安装前再次确认相关进程退出、文件无占用。超过合理等待期限就取消安装并恢复旧版使用。
6. 历史孤儿进程必须结合可信安装路径、进程身份及父子关系识别。不能只按 python-backend.exe 名称或 8765 端口批量结束进程。无法确认归属时说明原因，让用户处理。
7. 当前 restart_sidecar 仍是占位实现；需补齐真正的重启及状态重置，才能支持安装准备失败后的恢复。

## 5. 版本与发行约定

拟议：0.2.0 为首次带更新器的引导版本，0.2.1 为第一次真实升级验证。这里只是建议版本号，尚未发布。

- 用 Tauri 配置版本作为发行版本源，脚本同步 Cargo、前端版本并检查锁文件；提交号写入构建信息。
- 所有对外修复包严格递增版本，不覆盖同版本文件内容。
- 初始只发布 windows-x86_64 产物，主程序和后端使用同一发行号；启动健康接口增加后端版本、协议版本，防止新旧组件混用。
- 发布目录不可变；先上传安装包和签名，确认可下载后才更新稳定版清单，避免用户读到半成品。
- 测试版本先放独立测试入口，经真实升级验证再推广到稳定入口；首期不做按比例灰度。
- 现有 0.1.0 不会凭空获得更新器，需要用户最后手动安装一次引导版本。未安装的便携副本首期提示使用正式安装版，不伪装成已安装版本进行覆盖。

## 6. 更新文件放在哪里

推荐先用独立的公开发行仓库承载 GitHub Releases，代码仓库可继续保持私有。只公开安装包、签名、版本清单及更新说明。GitHub Actions 可用于自动构建并产出发行文件。[Tauri GitHub 发布流程](https://v2.tauri.app/distribute/pipelines/github/)

若主要用户所在网络访问 GitHub 不稳定，再选有 HTTPS 的对象存储和 CDN 作为主下载源。版本清单和安装包都必须能访问；上线前在目标网络测连通性与下载速度，不能仅保证本机能下载。

目前尚未确定实际仓库、域名和存储账号。方案不假设这些资源已经存在，也不在客户端嵌入私有仓库访问令牌。

版本清单需要表达发行版本、更新说明、时间和 Windows x64 对应的安装包地址及签名。可以采用静态清单，首期无需自建常驻更新服务器。[Tauri Updater 清单规范](https://v2.tauri.app/plugin/updater/#static-json-file)

## 7. 签名与安装权限

更新包必须通过 Tauri 更新签名验证。应用内放公钥；私钥在受保护的发行环境或 CI Secret 中保管并离线备份，不放 Git、不写入客户端或日志。密钥轮换需要旧密钥仍可签名的过渡版本；丢失私钥可能需要用户手动重装。

Tauri 更新签名与 Windows Authenticode 代码签名作用不同：前者验证更新来源，后者用于 Windows 发布者身份；不能承诺前者消除 SmartScreen 提示。首期规划明确二者职责，正式公开分发时再落实 Windows 签名证书。

保留当前 NSIS perMachine，不在第一次自动升级时改安装范围。更新安装采用有进度的 passive 模式，系统需要管理员权限时仍会出现 UAC，不能保证全程无提示。[Tauri Windows 更新模式](https://v2.tauri.app/plugin/updater/#installmode-on-windows)

## 8. 数据保留与恢复

- 以 `%APPDATA%/com.suxing.gallery/data` 为生产数据位置的现有基准，通过框架 API 定位，不拼接某位用户的绝对路径。
- 收藏、标签、目录配置、数据库保留；用户 ComfyUI 输出目录和原始图片不属于安装包覆盖范围。
- 首次引导版本排查历史数据目录；发现多个数据库或意外空库时展示位置与数量，不能用新空库覆盖旧库。多 Windows 账号数据分别属于对应账号，不静默合并。
- 备份配置及 SQLite 一致性快照；活动数据库使用 SQLite backup API，不能只复制 db.sqlite 而忽略 WAL。迁移前必须成功备份，检查可用空间。
- 数据库迁移带版本与事务；首期避免破坏性迁移。下载失败、签名失败都保持旧版继续运行。
- 安装器启动失败或用户取消 UAC 时恢复旧后端；验证 Windows 更新器是否已退出主程序，必要时由旧安装入口重新启动，不能仅靠前端 catch。
- 安装过程中断、磁盘写满或断电不承诺自动原子回滚。保存旧版安装包链接和备份恢复说明，优先发布更高补丁版本修复。降级前必须确认数据库兼容；已产生的新数据不能被旧备份静默覆盖。
- 新版首次运行验证版本匹配、健康接口、设置读取、图片列表和预览，再记录升级成功。失败日志可导出，不上传用户图片或路径。

## 9. 技术任务拆分

以下为拟新增/修改位置，新增文件尚不存在。

| 范围 | 拟议工作 |
|---|---|
| 现有 tauri.conf.json / Cargo.toml | updater、单实例、签名公钥、实际 HTTPS 入口、生成更新产物；核对工具链最低要求 |
| 现有 lib.rs / sidecar.rs / commands.rs | 单实例先注册、停止与等待、恢复、更新安装前协调 |
| 拟新增 src-tauri/src/updater.rs | Rust 端统一状态机、并发锁、超时、下载校验及安装协调 |
| 现有 SettingsModal.svelte | 关于与更新入口 |
| 拟新增 src/lib/updater.ts、components/UpdateDialog.svelte | 状态展示、用户选择、进度与重试 |
| 现有 backend/run_server.py 与后端路由 | 受控停止、任务状态、版本健康信息；本地控制接口需身份约束 |
| 拟新增 .github/workflows/release.yml | 测试、打包后端、构建签名安装包、生成清单、上传草稿发行 |
| 拟新增发布验证脚本 | 检查版本一致、产物齐全、签名与清单匹配、下载入口有效 |

优先让 Rust 拥有更新操作，前端只调用有限命令，避免绕过停止后端的前置步骤直接安装。若使用 JS updater/process 绑定，再按实际调用配置最小 capability。不得开放任意路径执行能力。

## 10. 分阶段交付

| 阶段 | 交付物 | 完成标准 |
|---|---|---|
| A：升级基础 | 单实例、版本统一、可靠退出、旧安装识别、数据目录诊断 | 同机重复启动、旧后端残留、不同安装路径均有确定行为 |
| B：本地更新闭环 | 更新界面、签名包、测试入口、备份与失败恢复 | 测试安装版从 0.2.0 升到 0.2.1，图片与配置保留 |
| C：发布与验收 | 正式 HTTPS 入口、CI、稳定清单、恢复文档 | 无开发环境的第二台 Windows 电脑完成首次安装和自动升级 |

每阶段单独提交，并运行对应回归测试。只有 C 通过才向普通用户提供自动更新；不以本机启动成功替代升级验收。

## 11. 必须通过的验收矩阵

| 场景 | 预期 |
|---|---|
| 无新版 / 同版本 / 旧版本 | 不安装、不重复提示 |
| 启动检查遇到断网、404、HTML、无效 JSON、超时 | 保持图库可用，手动可重试 |
| 下载中断或损坏 / 签名不匹配 | 不进入安装，不关闭当前图库 |
| 正在扫描时点击安装 / 重复点击安装 | 等待任务完成，只执行一次更新 |
| 旧后端残留 / 无关程序占用 8765 | 区分归属，不误杀；不能安装则保留可恢复状态 |
| 普通账号、管理员账号、拒绝 UAC | 安装或取消行为明确，取消后仍可打开旧版 |
| 默认路径、D 盘自定义路径、中文路径 | 原位升级，快捷方式不指向旧副本 |
| 旧版与新版并存 / 便携副本 | 识别冲突，不把文件写入错误目录 |
| 有收藏、标签、导入目录、历史图片的数据库 | 更新前后数量与关键字段一致，缩略图和原图可读 |
| 多数据目录、空库、缺失原图、迁移失败 | 提示差异，不覆盖旧数据；缺失原图不是更新损坏 |
| 低磁盘空间 / 安装中断 / 新版启动失败 | 明确恢复入口，备份可读，不承诺无条件自动回滚 |
| 无 Python、Node、Rust 的 Windows 测试机 | 自带后端正常启动与更新；ComfyUI 关闭仍能用图库 |
| 更新器正常但业务 API 配置错误 | 保存目录、扫描、图片及 WebSocket 的端到端测试必须拦截发布 |

## 12. 开始实施前的外部条件

默认按 Windows x64、稳定频道、用户点击安装执行。编码和本地测试可先开展。正式发布前仍需落实：发行仓库或 HTTPS 存储、可用的签名密钥保管方式、实际安装包下载入口，以及一台独立 Windows 测试环境。无需现在提交密码或私钥。

本轮仅交付方案与现状校验，没有生成签名密钥、创建远端仓库、配置定时任务或修改现有应用行为。
