# 项目现状与修改建议

核查日期：2026-09-09。核查基线：Git HEAD d564492，源码标记版本 0.2.1。本次仅梳理，不修改业务代码、图库数据或安装版本。

## 结论

直接修改正式项目源码，普通增删改查先在浏览器调试，再到 APP 验收。不要把 outputs/demo.html 当作正式功能入口。

如果“HTML 版本”指独立 demo.html，它只是早期交互原型，改动需要另行搬到正式项目；如果指 localhost 上运行的 Web 版，它与 APP 共用前端和后端，适合作为快速调试入口。APP 是最终交付环境，安装后的程序不会随源码编辑自动更新。

## 增删改查应该改哪里

| 需求 | 优先修改 | 验证入口 |
| --- | --- | --- |
| 布局、按钮、菜单、详情展示 | frontend/src/components/、App.svelte、app.css | 浏览器快速确认，再 APP 检查 |
| 新增导入或创建文件夹 | 前端 API/交互与 backend/app/routes/、indexer.py、repository.py | 隔离数据下验证实际入库，再 APP 验收 |
| 删除图片或文件夹 | 前端操作入口、后端路由与 repository.py | 验证数据库、原文件、缓存的处理语义 |
| 修改名称、标签、收藏、归属 | 前端 API/状态与后端路由、repository.py | 验证保存、刷新后保留及异常情况 |
| 查询、搜索、筛选、排序 | 前端查询状态、后端 repository.py，必要时 db.py | 验证结果、分页、FTS 与数据更新一致性 |
| 原生文件夹选择、启动、窗口、更新、安装 | frontend/src-tauri/ 及相关前端适配 | 直接在 APP 环境调试，最后验证打包版本 |

“增删改查”如果泛指新增、删除、修改功能，也沿用这个分工：界面与业务改共享源码，桌面集成改 Tauri 层。

## 建议执行顺序

1. 在正式源码实现一项完整功能，同时补充对应前后端测试；不回到旧 demo 重做。
2. 用 Vite + FastAPI 在浏览器快速调试共享界面与业务。
3. 在 APP 中检查真实 API/图片连接、原生交互及启动状态。涉及原生能力时从这一步开始调试。
4. 后端有变更时重新生成 Python sidecar；完成前端、桌面打包和相关回归，再交付安装包并记录 Git commit。

开发与正式数据路径可能不同：浏览器后端默认使用启动目录下的 data，可通过 SUXING_DATA_DIR 覆盖；Tauri debug 指定 backend/data，release 使用 app_data_dir()/data。测试前应明确数据目录，不能仅因两端画面不同就认为代码没同步。两端默认后端端口同为 8765，调试时需要明确由哪个后端占用和提供服务。

最终建议：以 APP 为产品交付目标，以共享源码为唯一业务实现，以浏览器作为普通功能的快速验证入口。
